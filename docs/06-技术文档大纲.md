## 3 系统架构设计（4 页）

**写什么**

- 分层架构：前端 Vue 3 + Vite 6 + TS + Element Plus / FastAPI HTTP 层 / 业务服务层  
  （library、retrieval、teaching、errors、llm）/ 存储层（Chroma 持久化 + SQLite 登记表 + 本地文件）。
- **照实际代码画架构图**：`backend/app/` 下为 `api / core / errors / knowledge / library / llm /
  models / retrieval / teaching`，入口 `app/main.py`；前端 `src/views` 四个页面  
  （Home / Teaching / Errors / Library）。
- 三条核心数据流（各配一张时序图）：
  1. 入库流：上传 → 校验(扩展名/大小/sha256) → 解析 → 分块 → 向量化 → Chroma upsert → 登记状态机。
  2. 问答/引导流：问题 → 分类 → 混合检索 → 覆盖度判定 → 分层策略 → 引用校验 → 响应。
  3. 截图分析流：图片校验 → OCR(视觉模型/本地 rapidocr) → 字段解析 → 复用检索与教学引擎。
- 存储设计：`storage/chroma`（集合 `library_chunks_v1`，512 维离线哈希向量 + 字面覆盖率）、  
  `storage/library/registry.json` 登记表、`storage/library/files` 原文件。
- 部署形态：Vite :5173 代理 `/api` → uvicorn :8000，单机单进程，SQLite/Chroma 均在 `storage/`。

## 4 AI 技术方案（6 页 · 官方明确要求重点阐述）

### 4.1 技术选型理由（约 1.5 页）

逐项写「选了什么 / 为什么 / 放弃了什么」，建议做成表格：

| 决策点       | 选择                                 | 理由                                                         | 放弃方案                    |
| --------- | ---------------------------------- | ---------------------------------------------------------- | ----------------------- |
| 检索增强      | 自建 RAG 链路                          | 一条链路约 200 行，可控、好调试、好讲解                                     | LangChain（黑盒、依赖重）       |
| 向量库       | ChromaDB `PersistentClient`        | 单机零服务、一个目录即库，无需 Docker/GPU                                 | Qdrant 服务端 / Milvus     |
| Embedding | 离线哈希向量（512 维）+ 字面覆盖率加权             | **无 Key、无外网、无 GPU 也能完整演示**                                 | 远程语义向量（列为可替换适配层）        |
| 生成模型      | OpenAI 兼容协议（可接 DeepSeek / 通义 / 智谱） | 只依赖最小公共子集 `messages/temperature/max_tokens`，换供应商只改 3 个环境变量 | 绑定单一厂商 SDK              |
| 截图识别      | 视觉模型优先 + 本地 rapidocr 兜底            | 断网可用；无 VLM 时仍有完整链路                                         | PaddleOCR（依赖重、torch 风险） |
| 前端渲染      | markdown-it + DOMPurify            | 模型输出必须清洗，防 XSS                                             | 直接 `v-html`             |

> 强调可替换性：Embedding 与 LLM 都是适配器接口，切换不改业务层——答辩高频追问点。

### 4.2 集成方式（约 2 页）

- 模型客户端 `backend/app/llm/client.py`：OpenAI 兼容 `/chat/completions`、2 次重试、  
  统一超时、任何异常抛 `LLMError`；`backend/app/teaching/engine.py` 在配置模型时用其润色 L1–L3，  
  **失败自动回退模板并在页面标注**。
- 配置加载：`pydantic-settings` 读项目根 `.env`，系统环境变量优先级更高；  
  密钥只存后端，`/api/health` 只回 `llm_configured` 布尔值，不回显密钥。
- 检索 → 生成的衔接：检索命中片段带 `doc_name / page / snippet / score` 注入提示词上下文，  
  要求结论标注来源编号；生成后白名单校验。
- 演示模式：`DEMO_MODE=auto` 且未配 Key 时，检索**真实执行**，回答由模板生成并显式标注  
  「演示模式 / 模板回答」，绝不伪装成模型输出。

### 4.3 优化策略（约 1.5 页）—— 这部分最容易拿分，务必写具体

- **抗幻觉**：检索分数低于 `RETRIEVAL_MIN_SCORE` 判「资料不足」→ 拒答，不编引用；  
  引用编号必须在本次命中集合内，越界剔除。
- **教学护栏（输出侧守门）**：L1/L2 无代码、L3 代码片段 ≤6 行、检测完整函数体自动收敛为骨架、  
  命中「完整代码 / 直接复制」话术自动降级；跳级请求服务端按 `current_level + 1` 强制压回。
- **分层策略由检索结果驱动**：L1 引用原文、L2 给排查顺序、L3 给诊断片段、L4 给迁移例题并标注 AI 生成。
- **稳定性**：模型超时/限流回退模板；OCR 失败引导手动粘贴；OCR 行号一律标 `line_estimated`  
  并在界面显示「识别，可能不准」。
- **性能与工程**：按内容 sha256 去重、删除同步清向量、分块保留页码与标题路径、  
  单 worker 避免 Chroma 文件锁、配置启动时读取。
- **安全**：上传白名单 + 大小/页数上限 + 文件名重命名；全模块无 `exec/eval/subprocess`；  
  DOMPurify 清洗；提示词用分隔符声明参考资料不是指令。

### 4.4 创新点说明（约 1 页，官方要求单列）

**技术创新点**

1. 检索结果不只塞给模型，而是**驱动分层教学策略**（检索 → 策略 → 护栏的三级链路）。
2. 输出侧的**答案泄露护栏 + 跳级拦截**，把「不代写作业」做成服务端强约束而非提示词约定。
3. **双通道 OCR 可编辑重分析**与「识别结果不等于事实」的标注机制。
4. **诚实的演示模式**：无 Key 时检索真实、回答模板化并显式标注，可离线完整复现。
5. 离线哈希向量 + 字面覆盖率加权，零外部依赖即可跑通 RAG 全链路。

**应用创新点**

1. 从「答题工具」转向「引导式学习」：四级提示逐级解锁，引导模式下必须先提交自己的尝试才能进 L3。
2. 面向真实教学场景的**可溯源引用**（文档名 + 位置），把 AI 回答变成可核对的学习材料。
3. 「无据则明说」的产品承诺，直接回应学术诚信与防抄袭诉求。
4. 教师侧知识库闭环：上传 / 失败原因可见 / 分块预览 / 删除同步清向量 / 重建索引。
